A plugin for the Hermes agent

hermes-hands

The agent thinks on your always‑on host. It works on the machine you are sitting at, as you.

Brain here, hands there

A capable agent wants an always-on machine: one loop, one memory, one set of skills. Your work is on a laptop that sleeps, moves and has your files on it.

Running a second agent on the laptop splits the memory in two. Mounting the laptop's disk on the host moves the files but not the shell, the tools or the user.

hermes-hands keeps one agent and moves only the last step. The loop, memory and skills stay on the host. Each shell command and file edit runs on a machine you name, over SSH, as your own user.

Hermes is not patched. The clients, the loop and the approval prompts are stock. The plugin is one terminal backend.

How a tool call travels

A session picks its machine once

  1. A target set with /hands <target> wins for that session.
  2. Otherwise the longest matching folder wins.
  3. Otherwise the default target is used.

A session never moves to another machine by itself. If its machine is down, tool calls fail and say which machine.

What you see

Where tools run

/hands names the machine, whether it answers right now, and the folder. Hermes Desktop shows the same in a chip on the status bar. 

Hands:   laptop (you@laptop)
State:   connected (41 ms)
Folder:  /home/you/Development/app
Why:     the session folder is in its path map

Approval prompts

Hermes' own prompt, unchanged, in every client. The plugin adds no approval path of its own, so nothing can skip the one Hermes has. 

⚠ approval required · recursive delete
rm -rf build
▸ 1. Allow once     3. Always allow
  2. This session   4. Deny

Commands that are your call

The agent can propose a command without running it. You run it with /run 2, or with a Run button in Desktop. It then goes through the approval prompt like any other. 

Proposed command #2

    $ make deploy

Run it with /run 2

When the laptop is asleep

A sleeping laptop is not an error to hide. It means you are not there. The agent is told plainly, and told not to work around it.

  1. about 3 s The tool call fails with an error that names the machine. The command was never sent.
  2. next 10 s Further calls fail at once. No call waits out a timeout.
  3. after that One call checks again. When the laptop is back, work resumes with no restart.

A link lost while a command is running is reported as no exit status. The command may have run. It is never retried, because a retry could repeat a write.

Limits

Read these before pointing it at a machine you care about.

No sandbox
An SSH target can do anything its user can. Hermes' approval prompts are the only gate. Keep them on.
Private Hermes APIs
It reuses Hermes' own local and SSH environments, which are not public plugin API. It refuses to load on a Hermes it has not been run against.
Editors
Hermes previews an edit by reading the file on the host. In an editor, patch only works where the same path exists on both machines.
One slow case
A machine that freezes in the few seconds before a call can take about seven seconds to report, not three.
After a switch
The agent is not told that /hands moved the session. Say so if it matters.
Lost on remote targets
Editor diagnostics, host-side search speedups, and checkpoints for /rollback.

The reason for each is in DECISIONS.md.

Install

Needs Hermes v0.23.2 on the host and key-based SSH from the host to your machine. No Python packages.

  1. Put the plugin in the profile's plugins folder and turn it on.

    git clone https://github.com/saxby-tools/hermes-hands.git \
  "$HERMES_HOME/plugins/hermes-hands"
hermes plugins enable hermes-hands

  2. Name your machines. This prints the settings. Add --apply to write them. 

    hermes hands init \
  --ssh laptop=you@laptop.example \
  --local mac \
  --prefix laptop=/home/you/

  3. Select the backend and check it.

    hermes config set terminal.backend hands
hermes hands status

The README covers every setting, the desktop half and the test rig.
